안녕하세요. 한국일보에서 프론트엔드 개발을 맡고 있는 가을입니다.

여러 서비스를 운영하다 보면 헤더와 푸터뿐만 아니라 내비게이션, 드롭다운, 추천 영역 등 다양한 UI 컴포넌트를 공통으로 사용해야 하는 상황이 생깁니다. 하지만 서비스마다 사용하는 프레임워크와 배포 주기가 다르다면 공통 UI를 일관되게 관리하기가 쉽지 않습니다. 컴포넌트 하나를 수정하더라도 여러 프로젝트에 변경 사항을 반영하고 각각 다시 배포해야 할 수 있기 때문입니다.

이 문제를 해결하기 위해 **Web Components를 기반으로 공통 UI를 구축하고, CDN을 통해 독립적으로 배포하는 구조**를 도입했습니다.

## 1. 왜 Web Components를 선택했을까요?

공통 컴포넌트를 구축하면서 가장 중요하게 생각한 조건은 두 가지였습니다.

> 1. 각 서비스의 기존 프레임워크와 배포 구조를 그대로 유지할 것
> 2. 공통 컴포넌트가 바뀌어도 서비스를 다시 배포하지 않고 반영할 수 있을 것

이를 위해 여러 방식을 검토했습니다.

| 방식 | 고려 사항 |
| --- | --- |
| 모노레포 | 저장소와 배포 구조를 통합하기 위한 변경 비용이 큽니다. |
| npm 패키지 | 변경 시 각 서비스에서 패키지 업데이트와 재배포가 필요합니다. |
| iframe | 독립성은 높지만 레이아웃 제어와 페이지 간 상호작용에 제약이 있습니다. |
| Web Components | 프레임워크에 종속되지 않으며 CDN을 통한 독립적인 배포가 가능합니다. |

최종적으로 브라우저 표준 기술인 **Web Components**를 선택했습니다.

Web Components의 핵심 기술 중 하나인 Custom Elements를 사용하면 개발자가 직접 HTML 태그를 정의할 수 있습니다.

```javascript
class CommonWidget extends HTMLElement {
  connectedCallback() {
    console.log('컴포넌트가 연결되었습니다.');
  }
}

customElements.define('common-widget', CommonWidget);
```

소비 서비스에서는 정의된 태그로 컴포넌트를 사용합니다.

```html
<common-widget></common-widget>
```

이 방식은 React, Astro 등 서비스가 사용하는 프레임워크와 관계없이 동일한 컴포넌트를 제공할 수 있다는 장점이 있습니다. 또한 JavaScript 번들을 CDN으로 제공하면 소비 서비스의 코드를 직접 수정하지 않고도 공통 UI를 업데이트할 수 있습니다.

다만 Web Components를 도입하는 것만으로 모든 문제가 해결되지는 않았습니다. 여러 서비스에서 안정적으로 사용하려면 스타일 관리와 SSR 지원을 추가로 고려해야 했습니다.

## 2. Shadow DOM의 스타일 격리와 초기화

Web Components를 구성하면서 Shadow DOM을 사용했습니다. Shadow DOM은 기본적으로 외부 CSS와 내부 스타일을 격리하지만, 모든 스타일의 영향을 완전히 차단하지는 않습니다. 예를 들어 `font-family`, `color` 같은 일부 CSS 속성은 외부 요소에서 상속될 수 있어서, 서비스마다 컴포넌트가 다르게 표시될 가능성이 있었습니다.

이를 해결하기 위해 **`<style>` 태그에는 초기화가 필요한 기본 스타일을 직접 정의하고, 나머지 스타일은 `<link>` 태그로 CDN에 배포된 스타일시트를 불러오도록** 구성했습니다.

```html
<common-widget>
  <template shadowrootmode="open">
    <style>
      /* 초기화가 필요한 기본 스타일 */
    </style>
    <link rel="stylesheet" href="https://cdn.example.com/style.css">
    <div class="widget">공통 컴포넌트</div>
  </template>
</common-widget>
```

이를 통해 서비스마다 CSS 환경이 달라도 컴포넌트의 스타일을 일관되게 유지하고, 공통 스타일시트를 별도로 관리하고 캐싱할 수 있도록 했습니다.

## 3. Declarative Shadow DOM으로 SSR 지원하기

일반적으로 JavaScript로 Shadow DOM을 생성하는 Web Components는 브라우저에서 스크립트가 실행된 뒤에 내부 UI가 렌더링됩니다. 그래서 서버가 전달하는 초기 HTML에는 다음처럼 빈 태그만 있을 수 있습니다.

```html
<common-widget></common-widget>
```

이 방식은 초기 렌더링이 JavaScript 실행에 의존하고, 검색 엔진이나 HTML을 분석하는 환경에서는 컴포넌트의 콘텐츠를 확인하기 어려울 수 있습니다.

이를 개선하기 위해 **Declarative Shadow DOM**(DSD)을 도입했습니다. Declarative Shadow DOM은 JavaScript 없이 HTML 마크업만으로 Shadow Root를 선언할 수 있는 기술입니다.

```html
<common-widget>
  <template shadowrootmode="open">
    <div>서버에서 렌더링된 콘텐츠</div>
  </template>
</common-widget>
```

브라우저는 HTML을 파싱하면서 Shadow Root를 생성하기 때문에, JavaScript가 실행되기 전에도 컴포넌트의 콘텐츠를 표시할 수 있습니다.

이를 활용해 컴포넌트의 배포 산출물을 크게 두 가지로 나눴습니다.

- **HTML Fragment**: 서버에서 렌더링된 초기 UI와 Shadow DOM 구조
- **JavaScript Bundle**: 이벤트 처리, 상태 관리 등 클라이언트 동작

소비 서비스는 서버에서 HTML Fragment를 가져와 초기 화면을 구성하고, 브라우저에서는 JavaScript를 실행해 필요한 동작을 연결합니다.

React로 구현한 컴포넌트는 기존 Shadow Root와 SSR 마크업이 있으면 `hydrateRoot()`를 사용하고, 없으면 Shadow Root를 생성한 뒤 `createRoot()`로 렌더링하도록 구성했습니다.

```javascript
if (element.shadowRoot) {
  hydrateRoot(rootElement, component);
} else {
  const shadow = element.attachShadow({ mode: 'open' });
  createRoot(shadow).render(component);
}
```

위 코드는 렌더링 방식을 간략하게 표현한 예시입니다. 실제로는 Shadow Root 내부의 마운트 요소를 확인하고 스타일시트를 연결하는 과정도 함께 처리했습니다.

이를 통해 **SSR과 CSR 환경 모두에서 동일한 컴포넌트를 사용할 수 있도록** 했습니다.

다만 모든 컴포넌트에 SSR을 적용하지는 않았습니다. 초기 HTML에 노출할 콘텐츠가 중요한 컴포넌트에는 SSR을, API 응답이나 사용자 상호작용에 따라 동적으로 구성되는 컴포넌트에는 CSR을 적용했습니다. 컴포넌트의 역할과 특성에 따라 렌더링 전략을 나눠 불필요한 복잡성을 줄일 수 있었습니다.

## 4. CDN을 활용한 독립적인 배포 구조

공통 컴포넌트를 여러 서비스에서 활용하려면 코드 재사용뿐 아니라 배포 방식도 중요했습니다. 컴포넌트를 수정할 때마다 모든 서비스를 다시 배포해야 한다면 공통 UI를 별도로 관리하는 장점이 줄어들기 때문입니다.

그래서 **GitHub Actions, Amazon S3, CloudFront**를 활용한 배포 구조를 구성했습니다. 전체 흐름은 다음과 같습니다.

```text
공통 컴포넌트 개발
        ↓
  GitHub Actions
        ↓
    Vite Build
        ↓
  HTML / JS / CSS
        ↓
    Amazon S3
        ↓
    CloudFront
        ↓
    소비 서비스
```

소비 서비스는 CDN에 배포된 HTML, JavaScript, CSS 리소스를 불러와 컴포넌트를 사용합니다.

이때 새 버전을 배포하더라도 모든 서비스에 즉시 반영되지 않도록 하는 것이 중요했습니다. 검증되지 않은 변경 사항이 여러 서비스에 동시에 영향을 줄 수 있기 때문입니다. 이를 위해 배포 과정을 **Publish(발행)와 Promote(승격)** 두 단계로 나눴습니다.

### Publish: 새 버전 발행

새 버전을 빌드해 버전별 경로에 업로드합니다. 이미 발행된 버전은 덮어쓰지 않는 불변 아카이브로 관리하며, 이 단계에서는 운영 서비스에 영향을 주지 않습니다.

### Promote: 운영 버전 승격

검증이 끝난 버전을 소비 서비스가 참조하는 별칭 경로에 반영합니다. 이 과정에서는 다시 빌드하지 않고, 이미 발행된 산출물을 그대로 사용합니다.

예를 들면 다음과 같은 구조입니다.

```text
components/
└── v1/
    ├── 1.0.0/
    ├── 1.0.1/
    ├── component.js
    ├── component.html
    └── latest.json
```

소비 서비스는 `v1/component.js` 같은 별칭 경로를 참조합니다. 새 버전을 검증한 뒤 승격하면 별칭 경로의 파일이 바뀌고, CDN 캐시가 갱신되면서 소비 서비스에도 반영됩니다. 문제가 생기면 이전 버전을 다시 승격하는 방식으로 롤백할 수 있습니다.

또한 컴포넌트별로 독립적인 배포 트랙을 구성해, 특정 컴포넌트의 변경 사항이 다른 컴포넌트를 쓰는 서비스에 불필요한 영향을 주지 않도록 했습니다.

결과적으로 **소비 서비스의 배포 독립성을 유지하면서도 공통 UI를 중앙에서 관리할 수 있는 구조**를 마련했습니다.

## 5. 캐싱과 초기 렌더링 최적화

CDN을 활용하면서 추가로 고려해야 했던 부분은 캐싱과 초기 렌더링 성능이었습니다.

특히 HTML과 CSS를 별도 파일로 제공하는 구조에서는 리소스 요청 순서에 따라 스타일이 적용되지 않은 UI가 잠깐 노출될 수 있습니다. 이를 **FOUC**(Flash of Unstyled Content)라고 합니다. 실제 구현 과정에서도 컴포넌트가 먼저 표시되고 CSS가 늦게 로드되면서 레이아웃이 순간적으로 깨지는 문제가 있었습니다.

이를 개선하기 위해 세 가지 방식을 적용했습니다.

### CSS 파일에 콘텐츠 해시 적용

```text
style.a1b2c3.css
```

CSS 파일 이름에 내용 기반 해시를 포함하면 스타일이 바뀔 때마다 새로운 URL이 생성됩니다. 덕분에 기존 파일은 오래 캐싱하면서도 변경된 스타일은 안전하게 제공할 수 있습니다.

### CSS 리소스 preload

초기 실행 스크립트에서 CSS 파일을 preload해, 브라우저가 스타일시트를 더 일찍 요청하도록 했습니다.

### 최소 스타일 인라인 적용

초기 렌더링에 필요한 최소한의 스타일을 인라인으로 넣어 CSS 로딩 전에 생길 수 있는 레이아웃 문제를 줄이고, 스타일시트가 준비되면 정상적인 UI가 표시되도록 구성했습니다.

이런 문제는 개발 환경이나 재방문 상황에서는 브라우저 캐시 때문에 잘 드러나지 않았습니다. 그래서 첫 방문이나 캐시가 없는 환경, 느린 네트워크 환경에서도 컴포넌트가 정상적으로 렌더링되는지 확인하는 것이 중요했습니다.

## 6. 컴포넌트와 서비스의 책임 분리

여러 서비스에서 공통 컴포넌트를 사용하면서, 컴포넌트가 어디까지 동작을 제어해야 하는지도 고민하게 되었습니다.

초기에는 공통 컴포넌트가 스크롤 위치나 페이지 상태를 직접 확인하고 UI를 바꾸도록 구현했습니다. 하지만 서비스마다 화면 전환 방식이 달랐습니다. 일반적인 스크롤 기반 페이지뿐 아니라 게임, 퀴즈, 인터랙티브 콘텐츠처럼 스크롤과 관계없이 상태가 바뀌는 서비스도 있었습니다. 이 차이를 모두 공통 컴포넌트에서 처리하면 새로운 콘텐츠 유형이 추가될 때마다 공통 코드를 수정해야 합니다.

그래서 **상태를 판단하는 책임은 소비 서비스에, 상태를 표현하는 책임은 공통 컴포넌트에** 두도록 바꿨습니다.

예를 들어 소비 서비스에서 다음과 같이 현재 상태를 선언합니다.

```html
<html
  data-state="play"
  data-theme="dark"
  data-gnb="menu"
>
```

공통 컴포넌트는 `MutationObserver`로 이 속성들의 변경을 감지하고 UI를 갱신합니다.

이 구조에서는 소비 서비스가 자신의 비즈니스 로직에 따라 상태를 결정하고, 공통 컴포넌트는 전달받은 상태를 표현하는 역할에 집중합니다. 새로운 콘텐츠 유형이 추가되더라도 기존 상태 규약을 활용할 수 있다면 공통 컴포넌트를 수정할 필요가 없습니다.

이를 통해 서비스별 비즈니스 로직과 공통 UI 사이의 의존성을 줄이고, 컴포넌트의 재사용성과 유지보수성을 높일 수 있었습니다.

## 마무리

이번 작업은 여러 서비스에서 사용하는 공통 UI를 일관되게 관리하기 위한 고민에서 시작했습니다. Web Components를 도입한 뒤에도 실제 서비스에 적용하는 과정에서 SSR, 스타일 격리, 배포, 캐싱, 상태 관리 등 다양한 문제를 마주했고, 이를 해결하면서 다음과 같은 구조를 마련할 수 있었습니다.

- **Web Components**: 프레임워크와 관계없이 재사용할 수 있는 공통 UI
- **Shadow DOM**: 스타일 격리와 기본 스타일 초기화를 통한 일관된 UI 제공
- **Declarative Shadow DOM**: SSR을 통한 초기 콘텐츠 렌더링 지원
- **CDN과 버전 관리**: 소비 서비스와 독립적인 배포 및 롤백
- **책임 분리**: 서비스의 비즈니스 로직과 컴포넌트의 표현 로직 분리

물론 Web Components가 모든 환경에서 최선의 선택은 아닙니다. 하나의 프레임워크와 배포 환경을 공유한다면 일반적인 컴포넌트 라이브러리가 더 간단한 해결책일 수 있습니다. 하지만 서로 다른 기술 환경을 가진 여러 서비스에서 공통 UI를 관리해야 한다면, Web Components는 충분히 고려할 만한 선택지라고 생각합니다.

### 앞으로의 과제

현재 일부 컴포넌트는 React를 기반으로 구현되어 있습니다. 앞으로는 Web Components에 특화된 경량 라이브러리인 **Lit으로 전환**해 번들 크기와 의존성을 줄이고, 컴포넌트 전용 저장소를 분리해 더 독립적인 개발·관리 환경을 만들 계획입니다.

이번 경험을 통해 컴포넌트를 재사용할 수 있게 만드는 것뿐 아니라, **각 서비스의 독립성을 유지하면서 안정적으로 운영할 수 있는 구조를 설계하는 것**이 중요하다는 점을 배웠습니다. 앞으로도 공통 컴포넌트의 구조를 개선하고, 여러 서비스에서 더 효율적으로 활용할 방법을 고민해 보려고 합니다.
